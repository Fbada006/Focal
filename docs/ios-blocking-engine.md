# iOS blocking engine: implementation notes

iOS blocking is built on Apple's Screen Time frameworks: FamilyControls (authorization and the app/website picker), ManagedSettings (applying blocks and Shields) and DeviceActivity (time-based triggers that run in an extension even when Focal isn't). See [ADR 0001](adr/0001-build-android-and-ios-in-parallel.md), [ADR 0004](adr/0004-shared-compose-ui-with-swiftui-islands.md), [ADR 0006](adr/0006-concurrent-focus-sessions.md).

Minimum deployment target: **iOS 17**. iOS 16 is the floor for individual (self) FamilyControls authorization and web-domain shields, but 17 avoids the widely reported iOS 16 Screen Time reliability bugs. Android's minimum is API 26.

## How it is built (T16)

- **Targets.** `iosApp` (the app, linking the shared Kotlin framework) embeds three Swift-only extensions: `ShieldConfiguration`, `ShieldAction` and `DeviceActivityMonitor` (T20). `iosApp/ShieldShared/FocalSnapshot.swift` is compiled into the extensions and `FocalStore.swift` (writes a session's blocked set into its store) into the app and the monitor; extensions never link `Shared` (ADR 0008). Every target has the Family Controls entitlement and the App Group `group.io.disruption.focal` (`APP_GROUP_ID` in `StartFocal.kt`). Extension bundle ids are the app's id plus `.ShieldConfiguration` / `.ShieldAction` / `.DeviceActivityMonitor`.
- **Engine.** `IosBlockingEngine.swift` implements the shared `BlockingEngine` and is passed to `startFocal`. Each Focus Session gets its own `ManagedSettingsStore` named `focal-session-<session id>` (`managedSettingsStoreName` in `IosBlockingSupport.kt`). `apply` clears the store and sets its apps (`shield.applications`), App Categories (`shield.applicationCategories`) and websites; `lift` and `pauseUntil` clear it. Stores are always opened by name, never cached, so a session applied before a relaunch, or by an extension, can still be lifted.
- **Websites.** Focal's websites are typed domains, but `shield.webDomains` only takes picker tokens. Domains are blocked through Safari's content filter (`webContent.blockedByFilter = .specific`), which shows the system's "restricted" page, not Focal's Shield. If that matters, the fix is letting the picker choose web domains as tokens.
- **Snapshot.** `IosSnapshotWriter` (shared `iosMain`) writes `snapshot.json` to the App Group container whenever Block Lists, Schedules or running sessions change. Snapshot v2 (T31) adds each running session's `scheduleId`.
- **Shield.** The configuration extension reads the snapshot, finds the running sessions (not on a Break) that block the app, App Category or domain, and shows the soonest-ending one as the title, then "+N more sessions also blocking", the time left and the same motivational line Android picks (`BlockingState`). The system renders it once, so the time left is "About N min" rather than a live countdown. If no session matches (say, a stale snapshot), it names the soonest-ending running session.
- **Shield buttons.** Close and Open Focal, both closing the Shield. Open Focal posts a local notification ("Open Focal", one at a time) that the user taps to open Focal, since a ShieldAction extension can't open its app. Nothing on the Shield ends a session or takes a Break.

- **Breaks (T20).** `apply` records what it applies for each session (`FocalAppliedSessions`: the blocked set, planned end and any Break's end, one file per session in the App Group) in the same step as it writes the store. `pauseUntil` first registers a DeviceActivity interval named `focal-break-<session id>` (`breakActivityName`) that ends at the Break's end; then it records the Break's end and clears the store. DeviceActivity intervals must last at least 15 minutes, so the interval starts 16 minutes before the Break's end, in the past; only its end matters. If the interval can't be registered, or there is no record to re-apply from, `pauseUntil` returns false and leaves the session blocking, and `takeBreak` takes the Break back and returns `BreakResult.Unavailable` (Home says the Break couldn't start): a Break that nothing would end if Focal were killed is not taken. The `DeviceActivityMonitor` extension's `BreakResumer` handles the interval's end: only if the record shows the session running with a Break that ends now (within a minute) and before the session's planned end, it re-applies the store from the record and appends `breakEnded` to `extension-events.json`. It reads the record, not the snapshot, because the snapshot is rewritten asynchronously and can be older than what the engine just applied (a Block List addition, a Break just taken). A Break that runs to the planned end ends with the session, so nothing is re-applied. The app ingests the event on launch, cutting the Break short if blocking came back early (interval ends are to the minute). `lift` deletes the record and clears the store, then stops the session's Break interval (`stopMonitoring`); if stopping ends the interval, the monitor finds no record and does nothing. Once a Break is over, the next `apply` (the catch-up at its end, or any re-apply) forgets it in the record and stops its interval the same way, so finished Breaks don't hold on to the system's limited DeviceActivity slots. The monitor itself doesn't stop intervals: it could race with a Break the app registers again. Every read and change of a record together with its store happens under `NSFileCoordinator` on the record's file, so the app and the monitor never interleave: the monitor can't re-apply an older set over a newer one, nor a session the app is lifting. `lift` also leaves an ended-session marker (`FocalEndedSessions`, one file per session) for extensions that read the snapshot. Backstops: while Focal is open, a timer runs the catch-up just after the Break's end; and every time Focal comes to the foreground (`focalDidBecomeActive`), it ingests the log and re-applies running sessions, so a Break whose interval didn't fire ends as soon as Focal is opened. If re-pausing a Break in progress fails then (`restore`, an edit or a Block List change), the session keeps blocking and the Break is recorded as over. Schedules and session ends (T31) have their own handlers in the same extension, keyed by activity name.
- **Event log size.** After ingesting, the app removes the events it ingested from `extension-events.json` (`IosContract.withoutIngested`), keeping unknown types, malformed entries and anything appended since it read the log. The app's compaction and the extension's append both run under `NSFileCoordinator`, so neither overwrites the other, and the log stays as small as what is still pending.

- **Uninstall Protection (T23, story 40).** `apply` sets `application.denyAppRemoval = true` in a Locked session's own store (`FocusSession.hasUninstallProtection`), and `nil` in other sessions' stores. The system combines every store, so Focal can't be deleted while any Locked session's store says so; `lift` clears the store, so protection ends with the last Locked session, with no store of its own to keep in sync. A Break (`pauseUntil`, and the monitor's re-apply at its end) only touches the Shield and web filter, so a Delayed session raised to Locked mid-Break keeps protection. Like the Shield, protection lasts until the app or an extension lifts the store; a session that ends while Focal isn't running has its store lifted by the monitor's `SessionEnder` (T31).
- **Broken (T23, ADR 0002).** Revoking Focal's Screen Time access clears its ManagedSettings, so blocking is defeated. Each launch and each return to the foreground (`ingestOnLaunch`) checks the permission gateway before re-applying sessions; if Screen Time access is missing, running Locked sessions become Broken (`FocusSessionService.checkPermissions`) and Home warns about them. Missing notifications don't break anything. Right after launch `AuthorizationCenter.authorizationStatus` can read `.notDetermined` for a moment, so the gateway waits up to a second for it to settle before reporting Screen Time missing.

- **Schedules (T31, stories 55–57).** The shared `DeviceActivityPlan` (core, unit-tested) turns switched-on Schedules and running sessions into DeviceActivity intervals; `IosSnapshotWriter` hands it to the Swift `IosDeviceActivityScheduler` after each snapshot write, whenever it changed. Each Schedule gets one repeating interval per day it runs, named `focal-schedule-<weekday>-<schedule id>` (Apple weekday, 1 = Sunday), from its start to its end on the same or (overnight) the next day; a Schedule on all seven days gets one daily interval (weekday `0`). Windows shorter than DeviceActivity's 15 minutes are registered 15 minutes long with a warning time marking the real end. The scheduler stops `focal-schedule-` and `focal-end-` activities no longer planned (switched off, deleted, session over), stops and re-registers one whose interval changed, and leaves activities registered with the same interval untouched. A `focal-end-` interval the monitor registered for a session it started is kept while that session's record (`FocalAppliedSessions`) lasts, even before the app has ingested the session, so switching off or editing its Schedule never leaves it without an end (ADR 0007: the running session runs to its end); before a plan stops or replaces a Schedule activity, the writer also ingests the extension log, so the plan itself lists that session's end. Session ends take priority within the activity limit (`DeviceActivityPlan.fitting`): the plan is cut to what fits beside Break intervals and the monitor's own session ends, dropped Schedule activities are stopped before session ends are registered, and if the system still refuses a session end, registered Schedule activities are stopped, last first, until it fits. Dropped Schedules are logged. A plan not registered in full (no Screen Time access, Schedules dropped) isn't cached as registered; it is registered again on every return to the foreground and right after Screen Time access is granted.
  - **Start.** The monitor's `ScheduleSessions` reads the snapshot's Schedule and Block List and skips the window if a session of that Schedule already overlaps it, as `evaluateSchedules` does (a window gets one session): one in the snapshot's `sessions` for the Schedule (its recent sessions, running or ended, even one ended early or started before the Schedule's times moved), a running one, or one with a coordinated record (`FocalAppliedSessions`; the app's engine records each session's Schedule) the snapshot doesn't list yet. Otherwise, in one coordinated step, it writes the new session's record (blocked set, planned end, name, Schedule and the window's activity name) and applies its store `focal-session-<random id>` with `FocalStore.apply` (with `denyAppRemoval` for Locked); then it registers the session's own `focal-end-` interval and appends `scheduleSessionStarted` with the blocked set. The window is worked out on the local calendar, as `ScheduleWindows` does: it starts at the latest time the clock read the Schedule's start and ends the next time it reads the Schedule's end, so overnight windows and windows spanning a daylight-saving change work, and a time in a skipped hour moves forward an hour keeping its minutes (02:30 becomes 03:30); a start firing outside its window does nothing. The Shield adds sessions with a record that the snapshot doesn't list yet (unless ended), so a Schedule session shows its name and time left before Focal ingests it.
  - **End.** At the interval's end (or its warning, for a short window) `ScheduleSessions` finds the sessions whose record names the window's activity and, inside each record's coordination, deletes the record, clears the store and appends `scheduleSessionEnded`, but only once the record's planned end has come: stopping the activity mid-window (Schedule switched off or edited) must not weaken the running session, and the app's engine writes a later end into the record when it extends the session, so an extended session runs on until its `focal-end-` interval ends it.
  - **Ingest.** On launch and each return to the foreground, `ingestOnLaunch` ingests the events, re-applies running sessions, and then evaluates Schedules as a backstop for a start that didn't fire. Without Screen Time access nothing is started (the session couldn't block, and a Locked one would escape the Broken check); the window starts on the first foreground after access is back, if still open. If the app had already started a window's session, the extension's duplicate is skipped and its store lifted (a window gets one session).
  - **Session ends.** Every running session also gets a one-off interval `focal-end-<session id>` ending at its planned end (starting 16 minutes earlier, in the past if need be, as Breaks do). The interval ends on the whole minute at or after the planned end. `SessionEnder` checks the session's record inside its coordination and lifts the store (deleting the record) only if the record's planned end has come; `edit` re-applies an extended session, writing the new end into the record in the same coordinated step as the store, so a callback for the old end, whenever it runs, never lifts the extended session. Editing a session's end also changes the plan, which registers its interval again for the new end. The Shield and Uninstall Protection so end on time with Focal closed. The app records Completed on next launch (`completeDueSessions`).
  - **Known gap.** If Focal is in the foreground when an extension starts a session, Home shows it only after Focal next comes to the foreground (that is when the log is ingested).

## Open risks to verify early

- **Uninstall Protection and revocation.** Not yet verified on a device: that `denyAppRemoval` in a named store stops deleting Focal from the Home Screen and Settings, that clearing the last Locked session's store allows it again, and what `authorizationStatus` reads after the user revokes Screen Time access in Settings (`.denied` or `.notDetermined`; either counts as missing).

- **Breaks while Focal isn't running.** Built as above (T20), but not yet verified on a device: that an interval starting in the past is accepted and its end fires on time, how late or early it fires, and that the monitor's re-applied store blocks again with Focal killed. If a past start is refused, every Break is refused with "Couldn't start the Break"; the fallback then is to let `pauseUntil` succeed on the foreground re-apply alone and say so in the Break UI.
- **Named store cap.** Each running Focus Session gets its own named `ManagedSettingsStore` (ADR 0006); Apple caps how many an app may use (reported as 50). Schedule sessions started by the extension add to it. Confirm the limit.
- **Monitored activity cap (T31).** DeviceActivity reportedly allows about 20 monitored activities per app. Focal uses one per Schedule day (one per Schedule that runs every day), one per running session's end and one per Break. Three weekday-only Schedules already take 15. Session ends take priority: Schedule activities that don't fit are dropped (and logged), and the launch backstop still starts their windows when Focal is opened. Nothing in the UI says a Schedule was dropped yet. If the cap bites, merge a Schedule's days into fewer activities or drop session-end intervals for sessions ending soon.
- **Schedules with Focal closed (T31).** Not yet verified on a device: that repeating weekday intervals and overnight intervals (end before start) fire on time; whether registering an interval during its window fires `intervalDidStart` at once; whether `stopMonitoring` fires `intervalDidEnd` (the handlers are written to be safe either way); that the monitor extension may register a session's `focal-end-` interval itself; that a short window's warning fires at its real end; and that a monitor-applied store with `denyAppRemoval` stops deleting Focal.
- **"Open Focal" from the Shield.** A ShieldAction extension cannot open the containing app directly; it can only close the Shield or run code in the background. "Open Focal" will most likely post a local notification the user taps to open Focal. Prototype and decide whether that friction is acceptable.
- **Schedule-started sessions begin in the DeviceActivityMonitor extension.** Built in T31: the extension appends `scheduleSessionStarted` with the Schedule, Strictness and blocked set, and Focal records the session (and its stats and Streak) when it ingests the log.

## Picking apps (T15)

- The Apps tab presents `FamilyActivityPicker` and stores the serialised `ApplicationToken`s and `ActivityCategoryToken`s on the Block List. It asks for Screen Time authorization first, since onboarding lets the user skip it.
- The selection uses `includeEntireCategory: true`, so a picked App Category stays a category token and covers apps installed later.
- Websites are not picked here. A Block List keeps websites as typed domains in the Websites tab on both platforms, so the picker's web-domain tokens have nowhere to go. The picker can't hide its websites section, so the sheet says so in its footer and won't save while websites are selected.
