# Focal v1 spec

Terms follow [GLOSSARY.md](../../GLOSSARY.md); decisions are recorded in [docs/adr/](../adr/).

## Problem Statement

People lose hours to apps and websites they open on reflex: social feeds, short video, news. Willpower alone doesn't hold, and the tools built into phones (Screen Time, Digital Wellbeing) are easy to dismiss and awkward to set up for recurring routines. Blocking only the app doesn't help either, because the same service is one browser tab away. Users want a single place to say "these apps and sites are off-limits during these times", with a level of strictness they choose, and to see that they are actually keeping to it.

## Solution

Focal, on Android and iOS, lets the user group apps, App Categories and websites into named Block Lists, and block them during Focus Sessions, started by hand or automatically by Schedules. Each Focus Session has a Strictness: Normal (end any time), Delayed (end only after an Exit Countdown, with up to three Breaks) or Locked (cannot be ended until it runs out). When a blocked app or website is opened, the Shield appears instead, saying which Focus Session is holding the block and how long is left, and offering only to close the app or open Focal. Any number of Focus Sessions can run at once, and a running session can only be made stricter. Focal shows focus time, outcomes and a Streak, all computed on the device; there are no accounts.

## User Stories

### Getting started

1. As a new user, I want to understand what Focal does before granting anything, so that I trust it with sensitive permissions.
2. As a new user on Android, I want a clear explanation before Focal asks for the accessibility service, so that I know why it needs it and what it does and doesn't read.
3. As a new user on iOS, I want to grant Screen Time access in one step, so that Focal can block apps on my own device.
4. As a new user, I want to be asked for notification permission with a reason, so that I understand it powers the running-session notification and the Shield's "Open Focal".
5. As a new user, I want to create my first Block List and start my first Focus Session right after setup, so that I get value immediately.
6. As a user, I want Focal to be asked for exact-alarm permission only when I create my first Schedule on Android, so that I'm not overwhelmed at setup.
7. As an Android user on Xiaomi, Samsung, Huawei or OnePlus, I want device-specific guidance on battery and autostart settings, so that my sessions aren't killed by the system.
8. As a user, I want a "Why did my session stop?" help entry, so that I can fix battery settings when something went wrong.
9. As a user, I want Focal to show clearly when a required permission is missing and how to fix it, so that I'm never unknowingly unprotected.
10. As a user, I want starting a Focus Session to be disabled while a required permission is missing, so that I don't start a session that can't block anything.

### Block Lists

11. As a user, I want to create a named Block List, so that I can reuse the same set of distractions across sessions and Schedules.
12. As a user, I want to rename and delete Block Lists, so that my lists stay tidy.
13. As a user, I want to be prevented from deleting a Block List that a running Focus Session uses, so that deleting it can't be used to escape blocking.
14. As a user, I want an Apps tab in the Block List editor, so that I can choose which apps to block.
15. As an iOS user, I want to pick apps and App Categories with Apple's picker, so that the selection is enforced by the system.
16. As an Android user, I want to pick individual installed apps from a searchable list, so that I can block exactly what distracts me.
17. As an Android user, I want to pick whole App Categories such as Social or Games, so that I don't have to find every app individually.
18. As an Android user, I want apps I install later to be blocked if their App Category is in my Block List, so that a newly installed social app isn't a loophole.
19. As a user, I want a Websites tab in the Block List editor, so that I can block the web versions of the services I block as apps.
20. As a user, I want to type a domain to block, so that I can block any website.
21. As a user, I want to pick from Suggested Websites for popular services, so that I don't have to remember every domain a service uses.
22. As an Android user, I want the Suggested Websites matching the apps I picked to be pre-selected, so that blocking Instagram the app also blocks instagram.com by default.
23. As a user, I want to edit and remove domains in the Websites tab, so that I can correct mistakes.
24. As a user, I want Focal to normalise what I type (strip "https://", "www.", paths), so that a pasted URL blocks the right domain.
25. As a user, I want blocking a domain to also block its subdomains, so that m.youtube.com is blocked along with youtube.com.

### Focus Sessions

26. As a user, I want to start a Focus Session now with a Block List, a duration or end time and a Strictness, so that I can focus immediately.
27. As a user, I want to see each running Focus Session with its Block List, Strictness and time left, so that I know what's blocked and until when.
28. As a user, I want an ongoing notification with the timer while a Focus Session runs, so that I can see it without opening Focal.
29. As a user, I want a Focus Session to end automatically at its planned end and be recorded as Completed, so that finishing takes no effort.
30. As a user, I want to end a Normal Focus Session at any time, recorded as Ended Early, so that Normal stays flexible.
31. As a user ending a Delayed Focus Session early, I want to sit through a 30-second Exit Countdown before I can confirm, so that I have a moment to reconsider.
32. As a user, I want the confirm button to stay disabled until the Exit Countdown finishes, so that I can't skip the wait.
33. As a user, I want leaving the Exit Countdown to cancel it, so that I can't wait it out while using the blocked app.
34. As a user, I want the session to keep running if I don't confirm after the Exit Countdown, so that only a deliberate tap ends it.
35. As a user in a Delayed Focus Session, I want to take a 5-minute Break from within Focal, so that I can handle something quick without ending the session.
36. As a user, I want blocking to resume automatically when a Break ends, even if Focal is closed, so that a Break can't turn into the rest of the session.
37. As a user, I want to see how many of my three Breaks are left, so that I can use them wisely.
38. As a user, I want Breaks not to move the end time or change the outcome, so that a session with Breaks can still be Completed.
39. As a user in a Locked Focus Session, I want no way to end, pause or shorten it inside Focal, so that I can commit for real.
40. As an iOS user in a Locked Focus Session, I want Uninstall Protection on, so that deleting apps isn't a way out.
41. As an Android user, I want Focal to detect when its blocking permission is revoked during a Locked session, warn me, and record it as Broken, so that defeating it has a visible consequence.
42. As a user, I want several Focus Sessions to run at once, so that a Schedule starting during my manual session isn't skipped.
43. As a user, I want an app or website to stay blocked while any running Focus Session includes it, so that ending one session doesn't unblock what another still blocks.
44. As a user, I want my running Focus Session to survive Focal being killed or the phone restarting, so that it doesn't silently end.

### Editing a running Focus Session

45. As a user, I want to add apps or websites to a running session's Block List and have them blocked immediately, so that I can tighten a session on the fly.
46. As a user, I want to extend a running session's end time, so that I can keep going when I'm in the zone.
47. As a user, I want to raise a running session's Strictness, so that I can lock myself in once I've started.
48. As a user, I want removals from a Block List used by a running Delayed or Locked session to take effect only after it ends, and to be told so, so that editing isn't a back door.
49. As a user, I want to be prevented from shortening a running Delayed or Locked session or lowering its Strictness, so that commitments hold.
50. As a user, I want edits to a Normal running session to apply freely, so that Normal stays flexible.

### Schedules

51. As a user, I want to create a named Schedule with days of the week, start and end times, a Block List and a Strictness, so that my routines are blocked automatically.
52. As a user, I want an end time before the start time to mean overnight, so that "22:00–07:00" works.
53. As a user, I want to switch a Schedule on and off, so that I can suspend it without deleting it.
54. As a user, I want to edit and delete Schedules, with changes affecting only future sessions, so that the running one isn't weakened.
55. As a user, I want a Schedule's Focus Session to start on time even when Focal is closed, so that I don't have to remember.
56. As a user, I want a Schedule whose start was missed (phone off) to start its session as soon as possible and still end at the scheduled end, so that a reboot isn't a loophole.
57. As a user, I want overlapping Schedules to each start their own Focus Session, so that combining routines just works.

### Shield

58. As a user opening a blocked app, I want the Shield to appear instead of the app, so that I don't drift in.
59. As a user opening a blocked website in a supported browser, I want the Shield to appear, so that the browser isn't a loophole.
60. As a user, I want the Shield to name the Focus Session holding the block (and "+N more" if several), so that I know why it's blocked.
61. As a user, I want the Shield to show time left and a motivational line, so that I'm encouraged to stay on track.
62. As a user, I want a Close button that closes the blocked app and returns me home, so that leaving is one tap.
63. As a user, I want an Open Focal button, so that I can manage my sessions deliberately in Focal.
64. As a user, I want there to be no way to end a session or take a Break from the Shield, so that blocking is never one tap away from being undone.
65. As an Android user, I want the Shield to appear without visible flicker, so that the blocked app's content doesn't flash.

### Stats

66. As a user, I want to see my focus time today and this week, so that I can see progress.
67. As a user, I want to see how many Focus Sessions were Completed, Ended Early and Broken, so that I'm honest with myself.
68. As a user, I want to see my current and longest Streak, so that I'm motivated to keep going.
69. As a user, I want a day to count toward my Streak only if it has a Completed Focus Session of at least 15 minutes, so that trivial sessions don't count.
70. As a user, I want a session crossing midnight to count for the day it ends, so that overnight Schedules behave predictably.
71. As a user, I want a Broken session to reset my Streak to zero, so that Locked carries weight.
72. As a user, I want Ended Early sessions to neither count nor reset my Streak, so that ending a flexible session isn't punished twice.
73. As a user, I want Schedule-started sessions to count exactly like manual ones, so that automation earns the same credit.

### Privacy

74. As a user, I want all my data to stay on my device with no account, so that my usage habits stay private.

## Implementation Decisions

- **Platforms**: Android (API 26+) and iOS (17+), built in parallel (ADR 0001). iOS development uses the Family Controls (Development) entitlement on a physical device; the Distribution entitlement must be requested for the app and every Screen Time extension before the first TestFlight build.
- **Modules** (ADR 0010): `shared/core` (pure Kotlin domain), `shared/data` (Room KMP, DataStore, curated data), `shared/ui` (Compose Multiplatform screens and view models), `shared` umbrella exporting the single iOS framework. The template's single `shared` module is split as the first step.
- **Domain core**: a session service in `shared/core` owns the Focus Session lifecycle (start, Break, Exit Countdown, end, outcome assignment, stricter-only edits, Schedule evaluation) and the Streak and stats calculations. It depends only on a clock abstraction, repository interfaces and the `BlockingEngine` interface.
- **BlockingEngine contract** (ADR 0006): per Focus Session, roughly "apply blocking for session X with this set of apps, App Categories and domains", "lift blocking for session X", and "pause session X for a Break until time T". Implemented per platform.
  - **Android**: one accessibility service detects foreground apps (`TYPE_WINDOW_STATE_CHANGED`) and, reading window content, the address bar of supported browsers (ADR 0005). It computes the union of all running sessions and shows the Shield as an accessibility overlay. Running sessions live in a foreground service; Schedules use exact alarms re-registered on boot and app update. See `docs/android-blocking-engine.md`.
  - **iOS**: one named `ManagedSettingsStore` per running Focus Session; the system enforces their combination. Schedules and Break resumption use DeviceActivity. Extensions are Swift-only (ADR 0008). See `docs/ios-blocking-engine.md`.
- **iOS snapshot contract** (ADR 0008): the app writes a small, versioned JSON snapshot of Schedules, Block Lists and running Focus Sessions to App Group storage; extensions apply it and append event records ("session for Schedule X started at T", "Break ended at T"). The session service ingests those records on launch and computes outcomes and stats. Extensions make no domain decisions.
- **Running-session copy** (ADR 0007): when a Focus Session starts, it takes its own copy of what it blocks. Additions to its Block List are merged in immediately; removals, earlier end times and lower Strictness are refused or deferred for Delayed and Locked sessions.
- **Locked on Android is best-effort** (ADR 0002): no blocking of Settings or uninstall; revoking a required permission during a Locked session, while Focal is installed, yields Broken. Uninstalling is an accepted escape that records no outcome and deletes local history.
- **Persistence** (ADR 0009, ADR 0003): Room KMP behind repositories for Block Lists, Schedules, Focus Sessions (outcome, Breaks taken, the session's blocked set) and ingested extension events; DataStore for small preferences. No backend, no accounts.
- **Curated data**: Suggested Websites (service → domains) and Android App Categories (package name → category, with Android's own category as fallback) ship as bundled data in `shared/data`, independent of the engines.
- **Domain matching**: typed input is normalised to a registrable host; a blocked domain also blocks its subdomains.
- **UI** (ADR 0004): shared Compose screens; SwiftUI only for Apple's app picker (hosted via interop) and the iOS Shield (ShieldConfiguration extension). Shield layout follows iOS's limits (title, subtitle, icon, two buttons) on both platforms: Close and Open Focal. On iOS, Open Focal likely posts a local notification that opens Focal.
- **UI architecture** (ADR 0011): hand-rolled MVI. Each screen's ViewModel exposes one immutable State (`StateFlow`), takes Intents through a single `onIntent`, and emits one-off Effects. Domain rules stay in `shared/core`, never in reducers.
- **Fixed values in v1**: Exit Countdown 30 s; Break 5 minutes, at most 3 per session; Streak minimum 15 minutes.
- **Assumed libraries**: Koin (DI), JetBrains Navigation Compose, kotlinx-datetime (all calendar and time-of-day logic), kotlinx-serialization (snapshot), kotlinx-coroutines/Flow.

## Testing Decisions

- **Good tests** exercise external behaviour through the session service's public API and assert observable results (outcomes, Streak, what the fake `BlockingEngine` was told to apply or lift), not internal state or call order details.
- **Main seam**: the session service in `shared/core`, driven with a fake clock and a fake `BlockingEngine`, covering: outcome assignment (Completed / Ended Early / Broken); Exit Countdown rules; Breaks (count, auto-resume, no effect on end time or outcome); concurrent sessions and per-session apply/lift; stricter-only edits and deferred removals; Schedule evaluation including overnight windows, days of the week and missed starts after reboot; Streak rules including the 15-minute minimum, day-of-end attribution, and Broken resets. Runs in `commonTest` on both platforms.
- **Snapshot contract**: round-trip and versioning tests for the iOS snapshot and extension event formats in `shared/core`, so Swift and Kotlin agree on the shape.
- **ViewModels**: where a screen has non-trivial logic, test it through MVI: send Intents, assert the emitted State and Effects, with fakes for the session service and repositories.
- **Not unit-tested in v1**: the platform blocking engines and extensions. They are verified manually on physical devices, including time-to-Shield measurement on Android and the iOS risks listed in `docs/ios-blocking-engine.md`.
- **Prior art**: none beyond the template's placeholder tests; these tests establish the pattern.

## Out of Scope

- App limits (daily time budgets), allow-list mode, per-app screen-time reports (v1.1).
- Accounts, cloud sync, backups, multi-device sessions.
- Social features: friends, leaderboards, shared sessions.
- Paid subscription and paywall.
- VPN-based "strict web blocking" on Android; website blocking in browsers Focal doesn't support.
- Blocking Android Settings or uninstall during Locked sessions; device-owner mode.
- Configurable Exit Countdown, Break length or Break count.
- Schedules with multiple windows per day, specific dates, alternate weeks, holidays or "skip today".
- An app-wide saved-websites library.

## Further Notes

- **Prototype these risks first**, before building on top of them:
  - iOS: resuming blocking after a 5-minute Break when DeviceActivity intervals may have a 15-minute minimum.
  - iOS: the cap on named `ManagedSettingsStore`s, which bounds concurrent sessions.
  - iOS: the friction of Open Focal via a notification.
  - Android: time-to-Shield and flicker on low-end devices and aggressive OEMs.
- **Play Console**: accessibility API declaration and review video (including window-content access for website blocking), `specialUse` foreground service justification, exact-alarm justification.
- **Apple**: request the Family Controls (Distribution) entitlement for the app and every extension bundle ID early.
